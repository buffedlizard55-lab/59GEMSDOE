Executive summary — how to make a submission

1. Download the file

From the status page, click “↓ Download the GeoTIFF” (or the single-TIFF ZIP — it contains exactly one GeoTIFF).

  • gems59-h59i-intensity-lattice-20261011T000000Z.tif — 139 KB, single band, float32.
  • SHA256 ed1b767f75804048382fc8baf61ff1edad6e9fd7b5b214def715ba5a1e290f6d — compare after download (sha256sum <file>).

2. Check the status banner before you upload

The status page carries an explicit two-part verdict at the top: DOWNLOAD: OK SUBMIT: NO. The current candidate is not cleared for a weekly slot because its local holdout score is below the published holdout best. Uploading is the owner's selector decision, made after reading the run card (docs/data/run_card.json).

3. Submit on DrivenData

  1. Open the competition submission page (rules: page 967).
  2. File to submit: choose the downloaded .tif (or the .zip containing exactly one GeoTIFF). The portal requires a single-band GeoTIFF matching the submission format's CRS, shape and geotransform.
  3. Note (optional, ≤ 140 characters): paste H59-I: presence-only MaxEnt/Poisson intensity, effort covariates, 1 km new-fault-density zoning, holdout break-even lattice.
  4. Click Create submission. The published cap is three submissions per week; the logged-in page shows remaining team capacity.

5. Reproduce locally (no manual data placement)

python3 -m venv .venv && .venv/bin/pip install -r requirements-lock.txt
# restore the hash-pinned 19-band GeoDAWN feature stack (GitHub mirror bridge) + band cache
.venv/bin/python scripts/prepare_data.py --fetch --cache-bands
# run the three pre-declared holdout experiments (~6 min on CPU)
.venv/bin/python scripts/run_intensity_lane.py --seed 20 --break-even 1.0
# build the submission through the fail-closed writer
.venv/bin/python scripts/build_submission_intensity.py --gamma 0.0 --collar 2 --break-even 1.0
# uniqueness audit against every pinned registry raster
.venv/bin/python scripts/audit_candidate_registry.py --candidate downloads/<file>.tif

The 418,912,844-byte feature stack is restored from five hash-pinned parts on the public mirror buffedlizard55-lab/6GEMSDOE and verified byte-for-byte (SHA256 4371c82e…23bc5); the DrivenData data tab itself is login-walled, so the bridge proves transport identity, not organizer origin. Nothing in this pipeline clicks Submit or spends a slot.
